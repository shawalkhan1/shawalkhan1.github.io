Compressing LLaMA-2 for CPU inference

A system-aware compression pipeline for LLaMA-2-7B, with runtime support for layers whose dimensions change after pruning.

Shawal Latif · AI on Edge Devices

Completed course project / Best Project Award

Code → Project report → Measurements (CSV) →
Problem My contribution Approach Evidence Limitations Next questions

The problem

A smaller set of weights is useful only if an inference runtime can execute it. Pruning introduced non-uniform attention and feed-forward dimensions, exposing assumptions in llama.cpp about the shape of transformer layers.

My contribution

I combined pruning, LoRA recovery, activation smoothing, and GGUF quantization, and adapted llama.cpp to obtain per-layer dimensions from GGUF tensor shapes for graph construction.

The implementation builds on LLM-Pruner, SmoothQuant, and llama.cpp. My focus was the connection between compression choices and an executable CPU inference pipeline.

Evidence & current status

The report compares five configurations on WikiText-2 perplexity, CPU throughput, peak memory, and model artifact size. Pruning alone records 45.9 tok/s versus 36.8 for FP16. Q2_K reduces the artifact from 25.10 GB to 2.10 GB, while perplexity rises from 7.18 to 10.38.

I received the course Best Project Award for the lowest perplexity and highest accuracy on the leaderboard. The award is separate from the five configurations recorded in the report.

Limitations

The report does not specify the CPU model or full benchmark settings. Its CPU figures are not Raspberry Pi-specific measurements. Quantized configurations also do not consistently improve throughput: Q4_K_M is slower than FP16 in the reported runs.

Next questions

The next question is how the quality-resource tradeoff changes on a defined edge device and for the languages and tasks people actually need. Reproducible device-level latency, memory, and quality evaluation would connect this runtime work to my HCI and low-connectivity research.
