LLM Twin

A pipeline for adapting a language model to a person's writing and connecting it to retrieval, deployment, and evaluation.

The problem

A useful personalized assistant requires more than a fine-tuned model. Data ingestion, retrieval quality, model adaptation, serving, and observability all affect the behavior people experience.

My contribution

I work across the full pipeline: ETL and streaming data, embeddings and retrieval, LoRA-based adaptation, agentic inference, and automated model operations. The original project architecture connects these components as a Feature / Training / Inference system.

How it works

↑ Select a pipeline stage to expand

Data. A multi-source ETL crawler pulls every digital trace (GitHub, Medium, personal sites) into a MongoDB warehouse. A Change-Data-Capture layer and a Bytewax streaming pipeline keep the twin's memory continuously fresh.
Feature. Text is cleaned, chunked, and embedded into a Qdrant vector database. The RAG layer uses query expansion, self-querying metadata filters, hybrid search, and a cross-encoder reranker.
Training. Llama 3.1 8B fine-tuned with QLoRA/LoRA (TRL + Unsloth) on an instruction dataset, then aligned with DPO/RLHF. Runs are tracked and evaluated with LLM-as-a-judge and RAGAS in Comet ML.
Inference. Served as a real-time AWS SageMaker endpoint behind a FastAPI microservice with a LangGraph agentic-RAG brain. Optimized with quantization (GPTQ/AWQ/GGUF), speculative decoding, Flash Attention, KV-cache, and continuous batching; benchmarked across vLLM, TGI, and TensorRT-LLM.
MLOps. Built on the Feature/Training/Inference (FTI) pattern, orchestrated by ZenML into deployable microservices, with CI/CD/CT via GitHub Actions, Opik observability, and drift detection that triggers automatic retraining.

Evidence & current status

The architecture uses MongoDB, Bytewax, Qdrant, TRL / Unsloth, LangGraph, FastAPI, Docker, AWS SageMaker, and ZenML. The pipeline explorer explains the role of each stage.

A linked demonstration is available, but this page does not present a measured latency, cost, or quality benchmark.

Limitations

Personalization and retrieval do not guarantee faithful representation of a person. Quality evaluation, provenance, privacy, and control over how the system acts remain important engineering questions.

Next questions

How much of a personalized retrieval and inference pipeline can run locally, and which capabilities should remain under explicit human control?
